# 荣珂评测集（eval/）

**它是什么**：把「成功率」这件事从**口头**变成**有口径的仪器**。
2026-09-19 外部评审的第一条实质性指摘是「从来没有成功率分母」。
分母不存在不是因为没人算，是因为没有可信的计算口径 —— 口径写在人脑子里等于没有。

**它不是什么**：它**不测**「科学结论正确性」。任务集里的判据全部是可程序化的
（文件在不在 / 工具真调没调 / 字数区间 / 门该不该拦 / 步数上限）。
「结论对不对」需要专家盲评，成本与流程是另一件事，别混进这个分母里假装测过了。

---

## 跑

```bash
PY="python"          # 或换成你机器上装了 python-pptx 的解释器

$PY eval/baseline.py                 # 从 runs/ 归档算基线
$PY eval/baseline.py --json          # 加一段机器读的 JSON
$PY eval/baseline.py --since 20260920   # 只看某天之后的归档（评测归零点）
$PY eval/baseline.py --self-test     # 正控 / 负控 / 承重自检 / 口径
```

退出码：**0 = 可报**（样本够）· **2 = NOT REPORTABLE**（样本不够，拒绝出数）· 1 = 读不到归档。
脚本与 CI 必须区分这三个码 —— 把"没测"当"通过"就是 M 型缺陷。

## 判据执行器 `run_tasks.py`（2026-09-26 补）

**它补的是哪一层**：`tasks.jsonl` 里那 74 条 check 此前**一条都没有被执行过**——
`baseline.py` 读 `tasks.jsonl` 只校验 JSON 形状（字段在不在、`checks` 是不是数组，
baseline.py:421-425），报的"成功"取自归档里的 `result.success`，而那正是**门自己的自述**。
所以「论文写得好不好」在这之前不是测不准，是**没有测**。执行器不新增任何门禁，
它只把已有判据**跑到交付物上**，从而让"某道门到底拦住了什么"第一次可回答。

```bash
$PY eval/run_tasks.py --self-test              # 离线自检（28 条断言 + 4 个承重探针），不花钱
$PY eval/run_tasks.py --replay                 # 用既有归档重算判据（零模型调用）
$PY eval/run_tasks.py --run --ready-only --repeat 3 --yes   # 真跑（花钱，必须显式 --yes）
```

| 判据词汇 | 含义 |
|---|---|
| `PASS` | 事实核过了，合格 |
| `FAIL` | 事实核过了，不合格 |
| `NOT AUDITABLE` | **拿不到事实**（工作区被清场 / 网关没回 token / 源数据不在）⇒ 不算通过 |

与 `figure.py` 同一条规矩：**`NOT AUDITABLE` ≠ `PASS`**。一次运行算"过"要求
**没有 FAIL 也没有 NA**；代价是报告里会显出一堆"没测到"，那是诚实。

退出码在 baseline 那三个之外再加两个，且 **3 与 4 必须分开**：
**3 = 仪器自检失败**（负控判不出"坏" ⇒ 仪器不可信，此时报任何 FAIL 都没有意义）·
**4 = 样本够但有 check 判 FAIL**。

负控集在 `negatives.jsonl`，每条是「一份已知合格/不合格的交付 + 一条判据 + **人先判的**期望」。
期望值不许从代码输出里抄 —— 抄来的断言只能证明代码等于它自己，那叫恒真。
所以自检里另有一节**承重探针**：把判据核心逐个抽掉，自检必须变红（不变红 = 那条断言恒真）。
已进回归套件（`regress.py` 的 `eval_run` 条目）。

## 四臂对照实验 `ablate_skill_gate.py`（2026-09-26 补）

问的是：**强制 `load_skill` 那道门，在荣珂上到底净赚还是净收税。**
外部证据（arXiv 2608.23067，带长度匹配无关对照）说注入"对的技能"平均让
Pass@2 **降 1.3–4.2%**、token **+72%~394%**，只有 17–36% 组合获益 —— 荣珂从没比过。

```bash
$PY eval/ablate_skill_gate.py --stages draft   # 只验设计：0 次任务运行、不依赖网关
$PY eval/ablate_skill_gate.py --pilot          # 1 任务 × 4 臂 × 1 次，量真实成本
$PY eval/ablate_skill_gate.py --sweep --reps 6 --yes
```

四臂：`full`（现状）· `no_skill`（去掉协议+门）· `text_only`（技能全文直投、门关掉）·
`placebo`（**等长无关文本**、门关掉）。真正的读数是 `full − placebo`：
它把"多一段字"本身的代价扣掉之后，剩下的才是技能的价值。

消融**不碰 `gate.py` 一行**：技能门整块包在 `if contract.stages:`（gate.py:448）里，
清空 `stages` 就是开关。⚠️ 但 `TaskContract.__post_init__`（contract.py:332）
见到空 stages 会**从目标文本重新推断** ⇒ 必须**构造之后**再清空，
`replace(c, stages=[])` 是关不掉门的（这条被抓进自检 ②，也已进回归 `ablate_design`）。

**第一次跑出来的三件事**（2026-09-26）：

1. 19 份归档里只有 **10 份**的 goal 精确对得上任务集（其余 9 份不认领、不并入分母）；
   认领到的 33 条 check **全绿**。全绿不是成绩 —— 因为可认领的只有两个最简单的写作任务。
2. `chars-blindspot` 这条负控显出仪器的边界：**一份通篇套话的稿子在字数判据上满分**。
   要测"写得好不好"得上 citation precision/recall，不是再加几条正则。
3. ★ 撞到上游缺陷：`tools.py:45` 的 `_RE_NUM` 带 `(?<![\w.])`，而**汉字算 `\w`** ⇒
   中文里紧贴汉字的数值一个都抽不到（`温度为47.3%、样本1280株` → 锚点为空）。
   后果是 `numeric_anchor` 在真实中文稿上会**虚判**（看着核过了，其实什么都没核）。
   修法在采集器不在执行器，已用 `num-na-glued` 这条 known-defect 钉住，防止被"顺手放宽"埋掉。


## 三条口径（写死在 `baseline.py` 顶部常量里）

| 口径 | 值 | 为什么 |
|---|---|---|
| 分母 | **不同任务数**，不是运行次数 | 同一目标跑 7 遍的成功率是「重试成功率」，不是「任务成功率」。混在一起报 = 拿一个数字掩盖两个含义 |
| 每任务重复 | ≥ 3 次 | 单次成功/失败分不清是能力还是运气 |
| 可报门槛 | ≥ 30 任务 **且** 每任务 ≥ 3 次 | 任一不满足 ⇒ `NOT REPORTABLE` + 退出码 2 |

**当前状态：`NOT REPORTABLE`。** 归档 9 场 / 只有 2 个不同任务 / 其中一个只跑过 2 次。
能报的只有「运行数 9 / 任务数 2」以及一批与样本量无关的观测（缓存、成本、未收敛尾部）。

## 任务集 `tasks.jsonl`

33 个任务 / 6 个桶。每行一个 JSON，`#` 开头是注释。字段：

```json
{"id":"w1-short-plain","bucket":"write-short","status":"ready","max_steps":12,
 "goal":"……（原样喂给内核的目标）",
 "checks":[{"kind":"chars_range","min":102,"max":138},
           {"kind":"tool_ok","tool":"load_skill","min":1},
           {"kind":"gate","expect":"pass"}],
 "why":"这条要测什么、为什么值得测"}
```

- `status`: `ready` = 今天就能跑；`needs-fixture` = 需先备材料。
- ⚠️ **`goal` 必须逐字等于喂给内核的那一串。** 跑的时候不许手打、不许加 markdown 装饰
  （`**`、`#`、引号）—— 基线按**目标指纹**分组，`**不要引用任何文献**` 与 `不要引用任何文献`
  是两个指纹，于是跑过的任务会被算成"不在任务集里"、**覆盖数静默缩水**。
  这个坑已实测踩到一次（20260919-092312 那场就是这么被判成"探索性运行"的），
  是仪器的**正确行为**（它拒绝把对不上的东西算进分母），但它不会替你去改任务集。
- `checks[].kind` 目前是**规格**（人读 + 未来的 runner 执行），`baseline.py` 只统计覆盖。
  **runner 尚未落地** —— 不要以为 `checks` 已经在拦人。
- `kind` 清单：`file_exists` / `tool_ok` / `tool_absent` / `chars_range` / `numeric_anchor` /
  `content_absent` / `input_tokens_max` / `steps_max` / `gate`（`pass` 或 `block`）。
- `gate: block` 是**对抗性正控**：这些任务设计成**必须被门拦下**。门放行才是失败。
  这一桶（7 个）是整份任务集里最值钱的部分 —— 它测的是「门会不会失灵」。

## 已知边界（别假装没有）

1. **不能离线复算门禁。** 归档 `session.json` 的 `events[kind=tool]` 只存
   `digest`（结果摘要哈希），**没有工具结果原文**。证据门第 4 条（验收覆盖）
   依赖 `tc.result` 文本 ⇒ **任何"只审归档"的外部评测在架构上不可能复核它**。
   推论：评测必须**在线重跑**，归档里的历史运行不可复用为证据。
   这也是「审计导出」这一产品化短板的技术根因 —— 见 `docs/评审回应-2026-09-19.md`。
2. **`usage` 字段名是 `input_tokens`/`output_tokens`**，不是 OpenAI 的
   `prompt_tokens`/`completion_tokens`。写脚本时读错名字会得到一堆 0，
   而 0 看起来像"这场没用 token"，不报错。（我本人第一版就这么翻过一次车，已写进自检。）
3. **一轮评测很贵。** 33 任务 × 3 次 = 99 场。按已实测的两个端点外推：
   短任务 53,584 输入 tok / 未收敛长任务 159,895 tok ⇒ 一轮 **5.3M–15.8M 输入 token**。
   这也是为什么「填 pricing 表」必须排在评测集**之前**：
   现在成本一律 `UNKNOWN`，等于跑完也算不出这轮多少钱。
   > ⚠️ 这一条原来还写着「和『打开前缀缓存』」。**那半句是错的，已删** ——
   > 2026-09-19 实测前缀缓存**一直在生效**（命中 95.8%），只是内核读错了字段名，
   > 把命中量报成 0。见 `cache_probe.py` 与 `docs/评审回应-2026-09-19.md` §3.0。
4. **★ 评分标准（`acceptance`）不是固定的 —— 这是个尚未修掉的效度缺口。**
   契约里的验收标准由**起草模型自己写**（`contract.DRAFT_SYSTEM`），同一个目标重跑，
   每次起草结果都不一样。实测（12 场归档 / 3 个任务组）：

   | 任务组 | 场次 | 用了几套不同标准 |
   |---|---|---|
   | `0c1a48c3` 低温诱导摘要 | 3 | **3 套** |
   | `72d32759` 冬虫夏草引言 | 7 | **6 套** |
   | `cf074742` Origin 散点图 | 2 | **2 套** |

   其中 `72d32759` 有一场只写了 **2 条**标准，而目标明说「论文引言」——
   那一套里**根本没有"体裁"这一项**。⇒ 按 `goal_id` 分组算出的"任务成功率"，
   **每次用的尺子并不是同一把**。

   `baseline.py` 现在会**检出并写在成功率正下方**（`rubric_drift()`，有正控/负控/承重自检）。
   **但这只是报出问题，没有修** —— 修法要让**同一任务的每次重复用同一套标准判**，
   即把 `acceptance` 钉进任务定义、并让内核支持注入固定契约（需要 CLI/内核加一个入口）。
   **在那之前，任何"任务级成功率"都要带着这行限定语来读。**
