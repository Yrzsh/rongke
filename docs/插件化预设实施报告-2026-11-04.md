## 3. 架构：对齐 dsh 的能力层栈

| dsh | 荣珂 |
|---|---|
| `- {id, name, config}` 插件行 | `CapRow` |
| agent preset 容器 | 预设文件的 `plugins[]` |
| bundle → profile → home → personal | `assemble(layers)`：base → 预设 → 个人覆盖 |
| zod schema 只在 mount 时校验 | `config_schema` + `mount_preset()` |
| `agentPresets.list().broken` | **`MountReport.broken` ← 唯一健康判据** |
| `complete: true` 结构性覆盖 | `op="replace"` |

**8 类能力 SPI**：`metric / gate / contract / mount / context / tool / prompt / stage`，
9 个内置实现放在 `rongke/caps_builtin.py`，全部由 `rongke/caps.py` 的注册器解析。
与 `plugins.py` 是**两条路**：老协议继续管第三方加工具 / 图型 / 图注与 CLI `--plugins` 台账，
本层管「组装这个 agent 本身」，互不污染。

**schema 纪律**：所有 `required=True` 的 config 项**不许带 default**
（`schema_discipline()` 是常驻元判据），防 dsh 的 `sampleOverCapGlobResults` 事故重演：
静态检查 67 项全绿、两个预设却因 mount 时缺必填而 `broken`。

**预设绑定本次 `run()`**，不是全局重建长命单例：`Manager.boot()` 是进程级对象，重建会撞
`busy()` 409，也会让追问串味。切换放在 `Rongke.run()` 的模块级串行锁内，收尾必须复原（见 §6）。

## 6. 真 bug：长命单例工具泄漏（已修）

**现象**（`_realp/run_preset_live.py paper-writing` 第一次真跑）：

```text
preset_mounted: preset=paper-writing healthy=True rows=9 broken=[]
tools_mounted: allow=60/67 schema_chars=43069
total=67 writing_metrics=True
```

预设声明「只绑定本次 run」，但 `writing_metrics` 注册进了 `Manager.boot()` 长命单例的
`ToolRegistry`，跑完没人撤 ⇒ **下一场不带预设的 baseline 任务也会背着 67 个工具**，
而且 `self.caps` / `gate.caps` 还停在 `paper-writing`（14 项门禁串味）。
这是「入口成立、收尾不成立」的假功能，必须显式确认。

**根因**：`load_capability_preset()` 传进 `mount_preset()` 的是 `dict(ctx)` **浅拷贝**，
挂载期写进去的登记信息外部读不到；且 `run()` 只有入口覆盖、没有 `finally` 复原。

**修复链**（四处，闭环而非打补丁）：

1. `ToolRegistry.unregister(name)` —— 按名撤销。
2. `WritingMetricsTool.mount()` —— 只在 `registry.get(...) is None` 时注册，并把
   `"writing_metrics"` 写进 `ctx["registered_tools"]`；**原本就有同名工具则不覆盖、不登记**
   （不撤别人的工具）。
3. `load_capability_preset()` —— 从**同一个 `live_ctx`** 读回 `registered_tools`，挂到
   `Caps.registered_tools`，并进 `to_dict()` 事件；新增 `Caps.invalidate_mount_cache()`。
4. `Rongke.run()` —— `try/finally`：按清单 `unregister()`、恢复
   `self.caps = self.gate.caps = self._baseline_caps`、作废 `refresh=once` 的 schema 缓存；
   开机预设自己注册的工具从撤销清单里排除；清理失败发 `preset_cleanup_error`，不静默也不改判任务结果。

**真 HTTP 双场验收**（`_realp/run_preset_leak.py`，10/10）：

```text
[before] total=66 writing_metrics=False
① paper-writing  : tools_mounted.total=67  → 跑完 total=66 wm=False
② baseline(不带字段): 无 preset_mounted，tools_mounted.total=66，schema_chars=42753
```

`schema_chars` 回到旧硬编码 42753，说明连「工具撤了、缓存里还看得到」这第二种泄漏也挡住了。

1. P0 时预设切换放在 `_run_serial()` 里，新增的属性读取被 `resume_test` /
   `mentor_workspace_test` 的「夹具覆盖真实代码要的全部协作对象」自检扫到 ⇒

   `re.findall(r"self\.([A-Za-z_]\w*)", inspect.getsource(...))` —— 它扫的是
   **源码文本，连注释一起扫**，于是「注释里的字」被当成「真实代码要这个协作对象」，
   3 套齐红。`workspace.js:530` 早有同类先例（「注释里不写字面量，ui_check 会判成引用」）。
   改掉注释措辞 + 在 `presets_live_test.py` 里**复刻同一套读/写口径**加常驻判据后，
   定向复验 4 套：`topic 2 / mentor_ws 7 / resume 0 / mentor-workspace 7 = 16 条`，
   `resume` 转绿、两个 mentor 各减 1。

⇒ 通用教训：**判据扫的是什么，就必须在什么上面写清楚**。它扫源码文本，
连注释都是被测对象；「实现已经降级了」不等于「判据读得到」。

`diff -u .backups/20261104-154601/rongke/loop.py rongke/loop.py` 证实本轮没碰
答复形态 / topic 段；剩下 **16 条是工作树既有红灯**。

### 另一个本轮暴露的判据盲区：回归数不出新探针的断言

`presets_live` 明明打了 59 条通过，回归却只计 **1 项**：探针用的是 `✓`（U+2713），

`--only presets_live` 读回 **59 项 / 0 失败**；再加一条夹具判据后为 **60 项**。
**判据自己读不到结果，比没有判据更危险** —— 这是「量了但量错东西」的一次实证。

### `ui_shot` 非零退出（既有，与本轮无关）

## 9. 怎么用

1. 控制台输入框上方点任务胶囊 → `PRESET` 被设好 → 发任务，事件流里会看到
   `preset_mounted`（不点胶囊 / 点「新对话」则不发，走 baseline）。
2. 追问自动沿用同一预设；`GET /api/presets` 看全部预设健康。
3. 要加一种新任务预设：在 `rongke/presets/` 放一份 JSON，`plugins[]` 里用
   `insert / patch / replace` 拼 9 行能力，`base: "baseline"` 继承；
   先跑 `python -m rongke --presets --live`（**只认 `broken`**），再重启控制台。
4. 要加一种新能力：在 `caps_builtin.py` 写类 + `@register`，`config_schema` 里
   必填项**不要给 default**；然后在调用点用 `caps.flag("行 id", "键", 旧值)` 取值 ——
   旧值就是「没挂这个能力」时的行为。

> 一句话：**判据、门、工具、上下文策略都搬进了预设；改行为不用再改内核，
> 但「改完有没有真的生效」仍然只能靠读回来的结果判定。**
