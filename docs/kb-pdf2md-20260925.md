> 起因：用户提出「荣珂 agent 需要有知识库模块，大概思路为通过 Zotero 插件将 PDF
> 转成方便 AI 读的 markdown 格式，再用 AI 解析写进 Obsidian 这种知识库。
> 核心目的为根据知识库指导用户后续实验，撰写综述或开题报告。」
>
> **本文所有数字都来自本次实跑**（命令与回显见 §3）。没有跑过的，一律标"未核实"。

| **PDF→Markdown** | ❌ **整条不存在** | 全仓 `grep zotero` / `obsidian` **零命中** |
| Zotero / Obsidian | ❌ **本机都没装** | `%APPDATA%\Zotero`、`%APPDATA%\obsidian` 均不存在 |

⚠️ `docs/mentor-mode-20260922.md` 里"知识库对 agent 完全不存在"那句**已经过期**
（那是接线之前的记录）。

⇒ 所以本次补的是**入库前那一环**：把 PDF 转成结构化 Markdown。
`litkb` 自己抽的是**纯文本**（丢标题层级/表格/阅读顺序），
而"方便 AI 读"要有**产物**可查，不能停在口号。

### 顺带一个必须说清的边界

**写进 Obsidian ≠ 进了荣珂的知识库。** 这是两套索引：

- Obsidian vault = **一个装了 .md 的目录**（给人翻）；
- 荣珂的 kb 库 = `litkb` 的 `index.db`（给 `kb_search`/`kb_ask` 查）。

两个都要，就得对同一份 PDF **各做一次**。这条写进了 `kb_to_obsidian` 的返回里，
因为它是用户最容易误解的一点 —— 以为写了 vault 就能问 AI 了。

## 2. 选型：为什么是 PyMuPDF4LLM

### 2.1 许可证**不是**分水岭（这条判断很重要）

子代理给出的通用结论是"干净 = marker/Docling/GROBID；被 AGPL 挡住 = PyMuPDF4LLM"。
**但那个结论对本仓库不成立**：

> 荣珂**已经在用 PyMuPDF** —— `rongke/figure.py` 的
> `_NEEDED_MODULES = ("matplotlib", "fitz")`。

⇒ AGPL 在本机**已是既成事实**，不是新负担。
   而且 `pip install pymupdf4llm` 顺带把 `pymupdf` 从 **1.28.0 升到 1.28.2**，
   而**完全 AGPL 化正是从 1.28.2 开始的**（[官方博客](https://pymupdf.io/blog/open-source-all-the-way-down-pymupdf4llm-goes-fully-agpl)，2026-08-10）。
   **这是一次真实的许可证变更，记在案** —— 不能当成"只是装了个包"。
   若将来要商用，正确动作是**连同已有的 `fitz` 一起重估**，而不是单独否掉新加的这个。

真正的分水岭是**依赖重量**：PyMuPDF4LLM 是纯 wheel、**无 torch**；
marker / MinerU / Docling 都要拖 torch + 模型权重。

### 2.2 对比表

| 工具 | 许可证 | torch/GPU | 备注 |
|---|---|---|---|
| **PyMuPDF4LLM** | **AGPL-3.0**（已核实） | **否** | 纯 CPU、无云依赖；无内置 OCR（另带 rapidocr）；公式弱 |
| marker | Apache-2.0 | 是 | 精度第一梯队，尤其双栏/表格/公式 |
| Docling | MIT | 是（有 CPU-only 路） | IBM 出品 |
| GROBID | Apache-2.0 | 否（Java） | **元数据 + 参考文献解析**是它的专长 |
| MinerU | ⚠️ **NOASSERTION**，**非标准 SPDX** | 是 | **未核实真实许可证，不要假设是 Apache** |

**未核实项**（不要当结论用）：所有工具的**安装体积**、**CPU 速度横向对比**、
**静默失败模式**；以及整个桥接生态（Zotero Integration / Obsidian Local REST API /
Zotero·Obsidian 的 MCP 服务器）—— **一个都没核实过**。

⇒ 所以本模块**刻意不依赖任何第三方插件**。Obsidian 库本质就是目录里的 `.md`，
   直接读写文件是最稳、最少依赖、也最不容易被上游改动打断的形状。

### 2.3 一个未解释的现象（如实记下）

`use_ocr=False` 比默认**少 1,999 字符**。差额可能来自被 OCR 救回的扫描页/图内文字。
**没有逐字比对过那 1,999 字符是什么** ⇒ "关 OCR 无损失"这句话**现在还不能说**。
所以本模块**不替用户断言收益**，只如实回报文字密度。

## 3. 实测数字（★ 核心证据）

夹具：`npj2024.pdf` —— 21 页、双栏、英文综述
（npj Vaccines 2024, DOI `10.1038/s41541-024-00834-y`）。解释器：系统 Python 3.12。

| 配置 | 21 页耗时 | 每页 | 产出字符 |
|---|---|---|---|
| 默认（开 OCR + 写图） | **53.2 s** | 2.53 s | 155,401 |
| `use_ocr=False` | 31.8 s | 1.51 s | 153,402 |
| `use_ocr=False, write_images=False` | **24.4 s** | **1.16 s** | 153,402 |

**读出来的三件事**：

1. **OCR 吃掉约 21 秒**，只多产出 1,999 字符（+1.3%）。
2. **写图又吃掉约 7 秒**，字符数**一个不差**。
3. ⇒ 默认配置比快路**慢 2.2 倍**，正文几乎一样。

⚠️ **而"默认开着 OCR"这件事是静默的** —— 控制台只打一行
`rapidocr_api using backend: rapidocr_onnxruntime`，**不会说慢了一倍**。
这正是本仓一贯在防的失败模式：不报错，只是慢。

⇒ 所以 `use_ocr` 默认 **False**，并把"这次走的哪条路"写进返回值（`used_ocr`）。

### 转换质量（同一份产物核的）

| 维度 | 实测 |
|---|---|
| 标题层级 | **19** 个标题 —— 结构被识别出来了 |
| 表格 | **132** 个竖线 —— 转成了 md 表 |
| 参考文献 | **220** 条编号条目，格式干净（`1. Trunz, B. B., Fine, P. & Dye, C. …`） |
| 双栏阅读顺序 | **正常** —— 正文连贯到末页版权声明，**没有左右栏串行** |
| 尾页 | 完整落到 `© The Author(s) 2024 / npj Vaccines \| (2024) 9:57` |

⇒ 对**英文双栏期刊论文**，够用且快。**公式（LaTeX）本次未评估** ——
   这篇综述公式很少，**不能据此下结论**。

## 5. 三条设计决定（都有血债）

### ① 同名笔记**绝不覆盖** —— 内容不同就存新名字

与 `kb_upload` 那边同一条纪律：**覆盖 = 静默换掉一份内容，且不报错**。
内容完全相同则**不重写**（幂等）；不同则存成 `名字 (2).md`，原件一个字不动。

### ② 不落临时文件 —— 正文走内存

第一版是"先落一个临时 md、再删掉"，**写出来当场撞了两条纪律**：

- `hygiene_test` 的「内核包里**零删除调用**」—— 删临时文件需要一次删除调用，
  而本仓对这个包的要求是一个都不许有（删除一律走 `_tkit` 的重命名路线）；
- 白落一份文件再删，本身就给"删失败/删错对象"留口子。

既然 `to_obsidian` 收的就是**字符串**，就没有理由经过磁盘。

### ③ 正文回传要么成功、要么明确失败（**这条真抓到了 bug**）

改成内存传递后，`loop.py` 那边**忘了传 `need_text=True`** ⇒ `conv.text` 是空串。
**内核自己的守卫拦下了它**：

> 「转换报告成功，但**正文没有回传**」

如果没有这条守卫，它会拿着空正文去写 vault ⇒ 产出一份
**看起来完全成功、实际是空壳**的笔记（典型的静默失败）。
⇒ 已把这条守卫钉成判据（`kb_convert_test` F 段）。

## 6. 测试怎么说

新增 `kb_convert_test.py`：**72 项断言全过**，含真转换。
按本仓定律，每条新增判据都配了**正控 + 负控 + 承重自检**
（把判据换成恒假/恒真，正控必须当场失守）。测试**真抓到了两个 bug**：

1. **`pages=0` 时误报"像是扫描件"** —— `chars_per_page` 恒为 0.0，
   于是把**「我不知道」渲染成了「我查出来它有问题」**（与 pricing 那边
   "UNKNOWN 不许写成 0"同源）。已修。
2. **`to_dict()` 用 `asdict()` 会把 15 万字符正文夹带回包** ——
   回包每步都发给模型 ⇒ **一次撑爆上下文，且不会报错**。已修（显式移除 `text`）。

**全套回归：1925 项断言 / 0 失败。**
其中 `kb_wire` 57、`kb_e2e` 51、`hygiene` 21（我修好了它，见 §5②）、
`kb_convert` 72 —— **全部绿**。
唯一非零是 `selftest`，原因是**环境变量 `COMMANDCODE_API_KEY` 没设**，
属环境问题，与本次改动无关。

- 双解释器 `py_compile` 均通过（3.12 + 3.13）。
- `snapshot.py save` 已做过（`rongke/loop.py` + `rongke/config.py`）。

## 7. 没做的 / 待办

| 事项 | 说明 |
|---|---|
| ❌ **不重写 `litkb`** | 它是**领域资产**，荣珂只编排不重写（与 figure/deck 同纪律）。重写 = 两处真相 |
| ❌ **不改 Zotero 插件** | 本机没装 Zotero；且**不把功能建在假设存在的第三方插件上** |
| ⚠️ **未接 Zotero 库路径** | Zotero 装上后，它的 storage 目录可作为 `convert_pdf` 的源路径 —— 但**没验证过** |
| ⚠️ **vault 路径要用户自己填** | `config.json` 的 `kb.obsidian_vault`。留空则工具**如实拒绝**，不替你猜库在哪 |
| ⚠️ **公式质量未评估** | 需要一份公式密集的论文重测 |
| ⚠️ **未做 A/B** | 没有拿 marker/MinerU 在**用户自己的语料**上对比过 |
| ⚠️ **扫描件路径未实测** | 只按文字密度**提示**，没有真拿扫描件跑过 |
| ⚠️ **Obsidian 侧未验证** | 本机没装 Obsidian ⇒ 只证明了"写出了一个带 frontmatter 的 .md"，**没有在 Obsidian 里打开过** |

### 建议的下一步

1. **装上 Obsidian**，把 vault 路径填进 `config.json`，人眼确认笔记能正常打开、
   frontmatter 被正确识别（这是唯一能证明"对 Obsidian 可用"的方式）。
2. 拿**你自己领域**的 2-3 篇论文各转一遍，看公式/表格是否够用。
3. 若要一次走完"转 md + 进 kb 库"，目前需要**两步**（`convert_pdf` 然后 `kb_ingest`）——
   可以合成一个工具，但**先确认两步都真的好用**再加，别拿一个没验过的组合动作
   去掩盖其中一步的问题。
