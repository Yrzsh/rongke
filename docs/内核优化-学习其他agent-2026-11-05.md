## 0. 一句话结论

上一轮的判定是「荣珂不是全插件，是**硬编码骨架 + 可替换插槽**，天花板 = 消费点数量」。
本轮没有继续加插件，而是**把骨架本身拆出四个可替换消费点**：SYSTEM 分节装配、通用贡献点、
门禁规则、工具可见性预算。学到的方向是「按任务少给、给准」，但因为 prompt caching 的
**稳定前缀硬约束**，没有照抄 ITR 的「每步动态重装配」，而是落成
**「开场按任务装配一次 → 整场冻结」**。

## 1. 调研：四条外部机制 + 一条硬约束

| 来源 | 机制 | 荣珂可取之处 | 不能直接抄的地方 |

### 1.1 本轮真正的判据：为什么不是「每步动态」

| 方案 | 上下文节省 | 前缀缓存 | 结论 |
|---|---|---|---|
| ITR 式：每步重算 system + 工具子集 | 每步都省 | **每步 miss** | ❌ 与稳定前缀直接冲突 |
| **开场按任务装配一次 + 整场冻结** | 一次性省，整场稳定 | **只 miss 1 次** | ✅ 本轮采用 |
| 改前：全量 static all-injection | 0 | 最稳 | ❌ 59 工具 42753 字符每场全发 |

点名回退是唯一允许的「中途变形」：只在模型真的点名时扩张一次，之后整场保持。

## 5. 两个方向都量（反向缺口，必须写）

1. **SYSTEM 装配那场工具数没变**：`lean=59 / baseline=59`。这一轮只裁提示段、不裁工具。
   把两件事分开验证，才不会把 A 场的成果说成 B 场的。
2. **工具预算只在显式声明时生效**：默认场 0 事件 59 个工具；`lean-context` 没写预算，
   所以它的工具数也不变。裁剪不是全局默认行为。
3. **点名回退只有单元正负控，没有真 HTTP 触发证据**：严格场 `tool_scope_expanded` **0 次**
   （说明清单稳定、没每步变形），但也意味着「模型真的点名被裁工具」这条路径尚未在真跑里出现。
4. **只量了字符数**：没有量 token / 成本 / 延迟的真实下降（网关 `cost=UNKNOWN` 老问题仍在）；
   也没量裁剪后答复**质量**的差异 —— 两场只是 `success=True`、`final` 非空。
   ⇒ **「省了字」不等于「质量更好」或「更便宜」**，这与上轮「14 项指标只证明配置在场」是同一个纪律。
5. **strict-v2 是行为变化，不是纯性能优化**：它从「死配置、模型看得见 60 个工具」变成
   「真裁剪、只看得见 24 个」。这是接活死配置的必然结果，但属于需要知晓的语义变更。
6. ★ **`complete:true` 接活曾让 strict-v2 的 system 6749 → 1893，同日已修**：
   `minimal_system()` 只留 4 个常驻节，写作流水线 `load_skill` 段与 PPT 段一起消失，
   而 strict-v2 自己声明 `scenes=["writing"]` —— 语义自相矛盾。真 HTTP B 跑的是
   「两三句话直接回答」的纯问答，当时没暴露出来。
   **修法（§9）**：`@rongke/prompt-sections` 加通用贡献点 `keep_sections`，
   `complete:true` 改走 `assemble(needed=...)` 分支（而不是把拼好的文本塞进
   `complete_text`，那样事件会把「保留了 1 节」谎报成「全丢」）；
   strict-v2 显式点名 `["writing"]`。修后真 HTTP **读归档 messages[0]：3046 字符**、
   `load_skill` 在、`compose_deck` 不在、交付纪律在。
   ⚠️ 当时**真写作长稿仍未跑**，只验证了 system 正文回位。
   ★ 同日后续已补跑并修掉两个「不可能通过的门」（契约 deck 位自相矛盾、
   工具预算裁掉 `load_skill`），两场现均 `success=True`（1024 / 899 字、
   12/0）——详见 `docs/文献检索插件化-2026-11-05.md` §9。
   **仍未量出稿质量 / token 成本 / 延迟**，别把「能收尾」写成「更好」。
   ⚠️ 修后 strict-v2 与 lean-context 的 system **逐字相同（都是常驻＋writing，3046）**，
   差别只剩工具预算与门禁判据 ⇒ **「按任务装配」的粒度还不够细**，这是下一轮的题。
7. **静态审阅捞出并已修一处真 bug**：`assemble()` 原先无条件先调 `split_sections()`，
   所以 SYSTEM 锚点漂移时，baseline 路径与「退回全量」异常降级路径**都会抛错** ——
   注释承诺「不许把任务打崩」在那种情况下不成立。当前 SYSTEM 锚点正常，未触发；
   修法 = `complete_text` / baseline 两条快速路径提到切分之前。
   **先量打红面**：`_realp/run_asm_degrade_probe.py` 修前 **3 FAIL** → 修后 **0**；
   再加 6 条常驻钉子（`system_assembly_test` 107 → 113/0），见 §6。
   ⇒ **「兜底代码依赖了出问题的那个东西」是 H 型缺陷的一个新形状。**
