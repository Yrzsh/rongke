# 荣珂 · 能力插件化架构（对齐 dsh），2026-11-04

> 用户判断：「其实我觉得应该做出像 dsh 那种插件类型的」。
> 本文把它落成**可执行的架构**，并附一份已跑通的最小原型。
> 结论先行：**方向对，而且不用从零做 —— 荣珂已经写好 60% 的地基，缺的是接线和插件化的对象。**

## 0. 先说清这句话指的是什么

dsh 的「插件类型」不是一个"能装第三方工具的接口"，而是三件事的合成：

1. **一切皆插件行**：persona、system-prompt 段、工具、intent-guard、playbook、子代理、权限
   —— 都是 `- id / name / config` 的一行，没有哪类能力天生住在内核里。
2. **预设是容器**：`@deepseek-ai/dsh-agent-preset` 自己不干活，`config.plugins` 把插件行挂进独立作用域。
   换行为 = 换预设，不改内核。
3. **层栈可叠加**：`dsh.bundle.patch` → profile `dsh.profile.bundles` → home patch → `--patch`，
   整棵组合树在 mount 时统一校验，健康只看一个出口 `agentPresets.list().broken`。

所以这件事对上一轮那 12 个卡点的意义是直接的：
**「想改一条判据就要改 `loop.py` / `gate.py` / `writing.py`」本身才是根因。**
插件化之后，Q1–Q7 / E1–E4 里至少 9 条变成「改预设里的一行」。

> 另一种读法（把荣珂整个做成一个可安装 bundle 挂到宿主）也顺带成立：
> 预设本来就是容器、能力包本来就可安装，最后一步只是把荣珂内核登记为一个 bundle
> （见 §6 Phase 4）。两条路不冲突，前者是后者的前提。

## 2. 目标形态：与 dsh 逐项对照

| dsh | 荣珂目标 | 备注 |

## 3. 预设长什么样（原型里已跑通）

`base.json` = **当前内核行为的等价基线**，`strict-v2.json` = 叠上去的一层 patch。
两层 `assemble()` 之后才 `mount`，顺序与 dsh 的层栈一致。

```json
// base.json（节选）
{"id":"citation","name":"@rongke/metric-citation",
 "config":{"bracket_pairs":["[n]"],"count_ref_table":false}}
{"id":"gate","name":"@rongke/gate-kernel",
 "config":{"measured_metrics":["chars","chars_delta_pct","paragraphs","sentences","citations","has_refs"],
           "evidence_fallback":true}}

// strict-v2.json（patch 层，节选）
{"op":"patch","id":"citation","config":{"bracket_pairs":["[n]","〔n〕"],"count_ref_table":true}}
{"op":"patch","id":"gate","config":{"measured_metrics":[...,"cliche_hits","cite_numbers",
                                    "cite_first_order","refs_n","absolutes","placeholders"],
                                    "evidence_fallback":false,"min_score":80}}
{"op":"replace","override":true,"id":"prompt","name":"@rongke/prompt-sections",
 "config":{"complete":true,"sections":["identity","tool-policy"]}}
```

**同一批类、只换 config** —— 这就是「修卡点不改内核」的机器形态。

### 12 个卡点 → 预设里的哪一行

| 卡点 | 改哪一行 | baseline → strict-v2 |
|---|---|---|
| Q1 抄原文即放行 | `gate.evidence_fallback` | `true` → `false` |
| Q2 量了 34 只认 6 | `gate.measured_metrics` | 6 → 14 项 |
| Q3 字数量纲漂移 | `chars.unit` / `display_unit` | `chars` / `chars_eq` → 同源 |
| Q4 〔n〕失明 | `citation.bracket_pairs` | `["[n]"]` → `["[n]","〔n〕"]` |
| Q5 追问零覆盖 | `followup.merge_new_constraints` | `false` → `true` |
| Q6 单一 draft | 新增 `draft_scope` 行 | 主稿＋附表分层 |
| Q7 软技能门 / 恒亮告警 | `stage.hard` / `dedupe_warnings` | `false` → `true` |
| E1 前缀算死 | `mount.refresh` | `once` → `per_stage` |
| E2 压缩滞后 | `context.compact_before_followup` / `target_chars` | `false/120000` → `true/60000` |
| E4 没字数工具 | `tool-writing-metrics.expose` | `false` → `true` |

E3（门只在交付时跑）与 E5（成本不可观测）属于**时机与计费**，接线时分别由 `stage` 的中途钩子与 billing 插件解决。

## 4. 原型：已跑通，24 项 / 0 失败

路径 `_realp/cappoc/`（`cap.py` 内核 / `caps.py` 九类示例 / `presets/*.json` / `verify_test.py`）。
**独立模块，不 import rongke、不修改任何产品代码。**

```bash
cd "<仓库根>/_realp/cappoc"
PYTHONIOENCODING=utf-8 python verify_test.py
```

- 3.12.10 与 3.13.14 **各跑一遍** `py_compile` + 全量验证：`24 项通过 / 0 项失败`，两个解释器一致。
- **正控**：`base` 单层 9 行全挂、`base + strict-v2` 层栈 9 行全挂、无冲突、门禁指标 6→14。
- **A/B 实测（拿上一轮 A 的 `讨论-初稿.md`，同一份 1404 字符稿，只换预设）**：

| | baseline | strict-v2 |
|---|---|---|
| 引注数 | **0**（复现 Q4） | **13**（修好） |
| 字数 measure / display | 1037 / 1080，**不一致**（复现 Q3） | 1080 / 1080，**一致** |

- **负控（必须能打红，两个方向都量）**：缺必填 `config.bracket_pairs`、模块名 resolve 不到、
  重复 id、`replace` 撞车未 override、个人层写进非法枚举、未知 config 键＋越界值 —— 全部 broken，
  且**坏件照样留在 `results` 里**不静默滤掉。
- **元判据**：所有 `required` 项都没有 `default`（防 dsh `sampleOverCapGlobResults` 事故重演）。

### 验证过程中修掉的一个真设计问题

第一版负控夹具叠了 `base` 层，重复 id 先在层栈冲突、行被挡在 `rows` 外 ⇒ 没走到 config 校验，
两条断言打红。查证后发现：**层栈冲突只记在 `conflicts`，没进 `broken`** —— 那 `broken` 就不是
唯一判据了，调用方还得读第二个字段，等于 dsh 那条教训白抄。
已改 `cap.py:mount_preset()`：冲突行也生成 `MountResult(ok=False)` 追加进 results。
夹具同时改成单层。修完 3.12 / 3.13 各 24/24。

## 7. 五条不许破的纪律

1. **健康只认 `broken` 一个出口** —— 不看 JSON 能不能解析、模块能不能 import、文件在不在。
   层栈冲突也算 broken（原型第一版漏了这条，验证时被打红后补上）。
2. **必填 config 不给默认值** —— `verify_pluginify` 67 项全绿而预设 broken 就是这么来的。
3. **坏件照样返回，不静默滤掉** —— 荣珂 `plugins.py` / `preset.py` 已有这条，接过去别弄丢。
4. **层栈合并之后才校验** —— `preset.py:272-310` 已写对，照抄。
5. **`replace` 必须显式 `override`** —— 对应 dsh `complete: true` 的结构性覆盖：
   不许一个升级带来的新段悄悄混进已收敛的提示词。

## 8. 边界

- 本轮**未改 `rongke/` 任何产品代码**，原型放在 `_realp/cappoc/`，无需回跑回归、无需重启控制台。
- 原型是**接口与判据的可运行证明**，不是生产实现：没有工具注册、没有真实 LLM 调用、没有接线。
- `baseline` 的"等价"指**配置值等价**（引注只认 `[n]`、门禁 6 指标、措辞兜底开等），不是完整内核行为的逐字节复刻。
- 未挂进 `regress.py`（原型属实验区）；P0 接线时必须挂，并补一份 `presets_live_test.py`。
- 三场实测本身仍是单次运行，不构成成功率；A/B 用同一份 A 稿，验证的是**判据差异**，不是稿件质量。
