> 触发：用户「对了，检索文献也做成插件」。

## 0. 一句话结论

改前「检索文献」是**散在内核各处的硬编码**：SYSTEM 的检索纪律、`contract.py` 的
`literature_fetch` 三路、无条件注册的 `verify_citation` / `literature_fetch`、
以及一个只改门禁指标、碰不到检索本身的 `lit-verify` 预设。用户点的「文献检索」胶囊
实际切到 `lit-verify` —— **选了等于没选检索能力**。

本轮把它收成 `rongke/caps_ext/lit_search.py` 一行能力 + 第 10 份预设
`lit-search.json`：检索纪律进 system、检索工具链在预算裁剪中被保住、检索后须有
真实文献表条目、胶囊真指向新预设。**内核只新增 1 个通用贡献点**（必留工具面），
其余四条贡献全部走上一轮已拆好的消费点；`baseline` 不点名时逐字等价，
`index.html` 文件 0 行、`baseline.json` 9 行未动、未 `--save`。

## 2. 落地的插件：`@external/lit-search`

文件 `rongke/caps_ext/lit_search.py`，随库自动发现（`external_cap_dirs()`），
**删掉这个 `.py` 就整条退回原样**。它不引入任何内核特判，只往已有通用贡献点写值：

| 贡献点（类属性） | 内容 | 内核消费处 | 效果 |
|---|---|---|---|
| `SECTION_TEXTS` | 719 字符检索纪律（7 条：先查库 → 找候选 → 留 DOI → 取全文 → 逐条核验 → 入库 → 缺件如实说） | `Caps.prompt_texts()` → `initial_messages` | 预设点名 `external-lit-search` 才拼进 system |
| `ESSENTIAL_TOOLS` | 7 个检索工具链（`kb_search`→`literature_search`→`literature_fetch`→`fetch_doi`→`verify_citation`→`kb_add`→`build_references`） | **本轮新增** `Caps.essential_tools()` → `ToolMount._build` | 工具预算裁剪时这 7 个一个不许丢 |
| `SYSTEM_SECTIONS` | `("writing",)` | `Caps.system_sections()` → `assemble()` | 保住写作流水线 `load_skill`，裁掉 `figure` / `deck` |
| `EXTRA_RULES` | 1 条门禁规则，分母是 `writing.lint` 的 `refs_n` | `gate._kernel_verdict` → `Caps.extra_rules()` | 检索后没有文献表条目即打回，不采信模型自述 |

### 三条不许破（写进插件自己的 docstring）

1. **工具名先查 `/api/tools` 再写**：提示段里点一个不存在的工具 = 给模型一条永远走不通的路。
   常驻判据专门验「段里点名的工具都在册」。
2. **必填 config 无 default 且必须接活**：`enabled` / `sources` / `require_citations`
   三项全必填。`sources` 真拼进段正文（换源 ⇒ 正文逐字变化），
   `require_citations` 真决定门禁规则在不在 —— 只躺在 JSON 里不算生效。
3. **工具不可达要如实说出口**：`literature_search` 来自外部 workbench，客户机没连 MCP
   时它不在 registry。**不算坏件**（能力本身没坏），但 `provides()` 必须点名缺了谁；
   没有 registry 的只读挂载检查则明说「[未验证] 可达性没测」。

### 唯一一处内核小改

`Caps.essential_tools()` 遍历 `ESSENTIAL_TOOLS` 贡献；`ToolMount.schemas_for/_build`
接受 `essential` 参数并让 `budget_report.essential` **读真实保住的名单**
（原来硬编码只报两个交付通道 —— 插件保住的工具会「生效了但事件不说」，是另一种
自称成功）。`loop.py` 装配点传入该值。`baseline` 无贡献 ⇒ 空元组 ⇒ 与旧表逐字等价。

**静态审阅（本轮补）**：生产路径里 `schemas_for` 只有 `loop.py:5022` 一个调用点，
`essential` 已传；`refresh != once` 只发 `schema_refresh` 事件、**不重算清单**；
`scope_fallback` 的 `append` 是唯一允许的中途变形。所以不存在「追问场漏传
essential 导致检索工具被裁」的第二条路径，有插件时「整场冻结」仍成立。

## 5. 反向缺口（别只报好消息）

1. **本机 7/7 可达是因为连了 MCP**：`/api/tools` 66 个工具里检索链全在。
   换一台没连 workbench 的机器，`literature_search` 会缺 —— 插件**如实说缺件、
   不算坏件**，但那种环境下「检索纪律进 system」并不等于「检索真能跑」。
   本轮没在缺件环境跑真 HTTP。
2. **门禁规则只有单元正负控，真 HTTP 未触发**：规则触发词要求
   「检索…文献…参考文献表」，双场故意用纯问答话术（避免外网检索耗时），
   所以 `refs_n` 那条没在真 run 里被点名。单元判据已验「正控 PASS /
   负控 FAIL / 不相关稿 UNKNOWN / 贡献即点名」，但**真长稿检索未跑**。
3. **只量字符数与工具数，没量检索质量、token 成本、延迟**：
   网关 `cost=UNKNOWN` 是老问题。「省了 18781 字符」≠「更便宜 / 答得更好」。
4. **24000 是新增的固定预算**：工具一增长，被裁的会是别的工具；
   必留面保住检索链与内核四个必留通道，但**其它工具被裁的语义影响未评估**。
5. **「删掉 `.py` 即退回原样」已做物理反事实**：`run_lit_search_unplug_probe.py`
   真把文件改名 → 新进程 `--presets --live` → 无条件恢复 + md5 校验，**13/0**。
   拔掉时 `lit-search` 报 `坏 2`（插件行 resolve 不到 + `prompt.sections` 白名单
   抛出「不存在的提示段 `external-lit-search`」），baseline 与 ext-answer-first
   仍绿；插回后 `✔ lit-search`、退出码 0。
6. 上一轮遗留：`strict-v2` 与 `lean-context` 的 system 骨架逐字相同（3046），
   「按任务装配」粒度还不够细；第 8/9 份预设的胶囊映射本轮已接，
   但 `Q6` 落盘稿锚定、成本黑箱仍在。
7. **真写作长稿已跑，但暴露并修掉两个既有死门**（见 §9）；
   其中「检索插件在真长稿检索任务里能否跑通」**仍未验**（会触发外网检索，
   本轮没跑），不能把「写作场成功」当成「检索场成功」。

### ★ 一个真反例：点名回退在真 HTTP 里触发过

上一版报告写「点名回退只有单元正负控、真 HTTP **0 次**触发」。本轮复跑
`run_tool_budget_probe.py` 时，strict-v2 场模型点了一个被裁掉的工具，
`tool_scope_expanded` **真触发 1 次**。这不是产品 bug —— 回退本就是设计允许的

事件 `frozen=True`、可见数单调 `+1`、不是每步重算**。改后 28/0，两种场态都通过。

## 9. 顺带修掉的两个「不可能通过的门」（真写作长稿场实测逼出来）

上一轮报告留了一句「真写作长稿未跑」。本轮补跑 `_realp/run_writing_long_probe.py`
（同话术、只换 `strict-v2` / 不带 preset，约 800 字三段正文，明写「不用做 PPT」），
结果**两场都 `success=False`**，各被打回 4 次、132.8s / 90.6s 后报阻塞。
这不是模型能力问题，是内核两处互斥规则把任务逼死了。

### 9.1 死门① 契约自相矛盾：禁止做 PPT，却声明需要产出 PPT

- **现场**：归档 `runs/20261105-193745` 的 `contract` 里，
  `forbidden=["查资料","写文件","做 PPT"]`、`constraints` 有「不做 PPT」，
  而 `needs_deck=true`；`deliver_attempt` 四次都带
  「本任务要产出演示文稿，但台账里一次 deck 体检都没有 … 必须先调 `audit_deck`」。
  模型原话：「要满足这一条，我必须先造一份 .pptx —— 那正是契约禁止的动作」。
- **根因**：`from_llm` 的 `needs_deck = 模型自报 or _looks_like_deck(...)`，
  而 `_looks_like_deck` 是**裸词表**（`_DECK_WORDS` 含 `ppt`），
  「不用做 PPT」里的 `ppt` 照样命中；模型这次又自报了 `true`。
  两处各自「照规则办」，叠起来就是互斥契约；第 9 条硬门读 `needs_deck`，
  要 `audit_deck`（必须先有 .pptx），而契约禁止产出 .pptx ⇒ **死循环**。
  `stages.infer_stages` 早就用 `_only_negated()` 处理否定语境，
  但 `contract.py` 的注释写着「刻意不处理否定语境」，理由是怕第二份拷贝。
- **修法（单源，不另抄）**：
  ① `_looks_like_deck` 直接复用 `stages._only_negated`（与 `infer_stages` 同一台机器）；
  ② `TaskContract.__post_init__` 加**契约自洽不变量** ——
     `needs_deck and _user_vetoed_deck ⇒ False`，覆盖 `from_llm` / `fallback` /
     调用方直接构造三条路径（`forbidden` 清单语义自带否定；原话则用
     「所有命中的 deck 词都只出现在否定语境」判定，避免一刀切误杀）；
  ③ `DRAFT_SYSTEM` 加铁律：禁止清单与 `needs_deck` 不许打架。
- **判据** `contract_deck_veto_test.py` **24/0**：三条构造路径、正反两方向
  （把「不用做 PPT」换成「并做一版 PPT」必须翻回 `True` 且推得出 `slides`）、
  窄表不变、否定机器单源。`deck_test` **534/0**。
- 🪤 **中途真回归**：一开始把 `_looks_like_deck` 改成直接读 `_DECK_WORDS`，
  让 `deck_test:9.1`（替换 `_DECK_STRONG` 做承重自检）失效 ⇒ 534/1。
  保留别名后 534/0 —— **最小改动面比"看起来更干净"更重要**。

### 9.2 死门② 预算裁掉了硬门要求的工具

- **现场**：修完①后默认场转绿（899 字、`success=True`），但 strict-v2 仍
  `success=False`、42.3s 报阻塞，模型原话：「证据门要求先装载阶段专属技能
  `load_skill("nature-writing")`，而本执行体的工具清单里**没有 `load_skill`** …
  我不愿编造一个假的 `call_seq` 冒充技能装载记录」。
- **根因**：上一轮把 `schema_chars_budget` 死配置接活后，strict-v2 的 18000
  预算把 `load_skill` 裁掉了（它在 `dropped` 名单里），而门禁第 6 条
  「阶段专属技能必须装载」是**硬门**，且 `CompletionGate.LOADER_TOOLS`
  明确只认 `load_skill` / `read_skill`。`ESSENTIAL_TOOLS` 当时只有
  `deliver_task` / `report_blocker` 两个交付通道 ⇒ 又是一个不可能通过的门。
  这是「strict-v2 是行为变化不是纯优化」那条边界的实际代价。
- **修法**：`ESSENTIAL_TOOLS` 补 `load_skill` / `read_skill`；钉子判据
  「`CompletionGate.LOADER_TOOLS ⊆ ESSENTIAL_TOOLS`」；夹具真注册这两个工具；
  过期文案「事件只列两个交付通道」改为集合包含语义。
- **修后实测**：strict-v2 **60→25 工具 / 43069→17893 字符**（仍
  `within_budget=True`）、检索插件场 **59→33**、essential **11 个**
  （7 检索链 + 4 内核必留）；真写作长稿**两场 `success=True`**
  （1024 / 899 字），`run_writing_long_probe` **12/0**；
  三场既有真 HTTP 对照 A 24/0、B 28/0、C 33/0 全绿。

### 9.3 通用教训（比这两处修复更值钱）

> **门会拦的动作，工具清单必须够得着；契约禁止的动作，意图位不许抬起。**
> 两个死门都是「两处各自正确的规则叠成互斥」——与 `answer_only` 那次
> 「空验收标准 + 一律打回」同族。修法都不是放松门，而是**让契约与工具面自洽**；
> 预算宁可如实报 `essential_over_budget`，也不许把硬门拆了还回 `ok`。

⚠️ 仍未做：检索插件在**真长稿检索任务**里能否跑通（会触发外网检索）、
裁剪后的答复质量 / token 成本 / 延迟，都没有量；别把「写作场成功」当成
「检索场成功」。
